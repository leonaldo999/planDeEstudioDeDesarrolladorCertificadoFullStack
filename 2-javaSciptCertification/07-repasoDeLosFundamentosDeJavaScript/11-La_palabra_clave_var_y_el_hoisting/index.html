🚀 Introducción

En este módulo, exploraremos la palabra clave var y el concepto de hoisting en JavaScript. Comprender estos conceptos es fundamental para escribir código limpio y evitar errores comunes.

Tema 1: ¿Qué es la palabra clave var y por qué ya no se recomienda usarla?

La palabra clave var en JavaScript es una de las formas originales de declarar variables. Ha formado parte del lenguaje desde sus inicios y, durante muchos años, siguió siendo el método principal para crear variables. Sin embargo, a medida que JavaScript evolucionó y los desarrolladores adquirieron más experiencia con el lenguaje, se hicieron evidentes ciertos inconvenientes del uso de var, lo que llevó a la introducción de let y const en 2015.

Cuando declaras una variable con var, esta adquiere un ámbito de función o un ámbito global. Esto significa que, si declaras una variable dentro de una función usando var, solo se puede acceder a ella dentro de esa función. Sin embargo, si la declaras fuera de cualquier función, se convierte en una variable global a la que se puede acceder en todo el script. Este comportamiento a veces puede dar lugar a resultados inesperados y hacer que tu código sea más difícil de entender.

Un problema con var es que permite redeclarar la misma variable varias veces sin generar un error. Esto puede provocar sobrescrituras accidentales y dificultar la depuración.

12345678910111213 
var num = 5;
console.log(num); // 5

// This is allowed and doesn't throw an error
var num = 10;
console.log(num); // 10

Comportamiento de Ámbito Global/Función

Análisis de Redesclatación:
🟢 Asignación Inicial (Línea 1): La variable num se registra en el entorno actual y toma el valor numérico de 5 sin restricciones.
🟢 Sobrescritura Permitida (Línea 5): A diferencia de let o const, volver a usar var num es totalmente válido para el motor de JS, mutando silenciosamente el espacio original a 10.
JAVASCRIPT ENGINE AUDIT:
• Strict Mode: PASSED (No genera SyntaxError)
• Variable Shadowing: OVERWRITTEN (El valor original se pierde por completo en el mismo contexto léxico)

💡 Peligro en producción: Permitir la redeclaración de variables sin avisar puede hacer que pases por alto errores tipográficos en scripts grandes, reemplazando datos de variables existentes de manera accidental.

El problema más importante de var es que no tiene ámbito de bloque. Las variables declaradas con var dentro de un bloque, como una instrucción if o un bucle for, siguen siendo accesibles fuera de ese bloque.

12345678910 
if (true) {
  var num = 5;
}
console.log(num); // 5

Análisis de Fuga de Ámbito (Scope Leak)

Comportamiento del Bloque:
🟢 Ignorancia de Bloque (Líneas 1-3): El motor de JavaScript procesa el bloque if, pero al detectar la palabra clave var, asocia la variable al ámbito de la función contenedora o al contexto global, no al bloque de llaves.
🟢 Acceso Externo (Línea 4): Como la variable se "fugó" del bloque decorativo, console.log(num) puede leer perfectamente el valor de 5 desde afuera.
SCOPE MANAGER REPORT:
• Block Scope: NONE (Las llaves del if no aíslan la variable)
• Variable Status: LEAKED / GLOBAL (Visible y expuesta en todo el script exterior)

💡 Por qué usar let / const: Si modificas el ejemplo reemplazando var por let, la línea 4 lanzaría de inmediato un error de tipo ReferenceError, protegiendo la integridad del flujo.

Este comportamiento puede provocar fugas de variables no intencionales y hacer que tu código sea más propenso a errores.

Debido a estos problemas, el desarrollo moderno de JavaScript ha dejado de lado en gran medida el uso de var para dar paso a let y const. Estas palabras clave ofrecen un ámbito de bloque que se ajusta mejor a cómo funciona el ámbito en muchos otros lenguajes de programación.

Además, no permiten la redeclaración dentro del mismo ámbito, lo que ayuda a evitar sobrescrituras accidentales.

Si bien var sigue formando parte de JavaScript y funciona en todos los navegadores, por lo general se recomienda utilizar let y const en el desarrollo moderno de JavaScript. Estas palabras clave ofrecen reglas claras de ámbito, ayudan a evitar errores comunes y hacen que el comportamiento de tu código sea más predecible.

Tema 2: ¿Qué es el hoisting?

El hoisting es un comportamiento de JavaScript que suele confundir a los principiantes, pero entenderlo puede ayudarte a evitar errores sutiles en tu código. En términos sencillos, el hoisting es el comportamiento predeterminado de JavaScript de mover las declaraciones al inicio de sus respectivos ámbitos durante la fase de compilación, antes de que se ejecute el código.

Para entender el hoisting, es importante saber que JavaScript se ejecuta en dos fases: la fase de compilación y la fase de ejecución. Durante la fase de compilación, el motor de JavaScript revisa tu código y configura el espacio de memoria para las variables y las funciones. Aquí es donde entra en juego el hoisting.

Comencemos con el hoisting de variables: cuando declaras una variable usando la palabra clave var, JavaScript eleva la declaración al inicio de su ámbito. Sin embargo, es fundamental tener en cuenta que solo se eleva la declaración, no la inicialización. Esto significa que puedes usar una variable en tu código antes de haberla declarado, pero su valor será undefined hasta que realmente le asignes un valor.

12345678910 
console.log(x); // undefined
var x = 5;
console.log(x); // 5

Fase de Creación y Memoria (Hoisting)

Asignación en Memoria Temporal:
🟢 Fase de Compilación (Línea 1): El motor de JavaScript detecta la declaración var x en la línea 2 y reserva espacio en memoria inicializándolo automáticamente con undefined. Por eso la primera lectura no falla.
🟢 Fase de Ejecución (Línea 2): El código llega a la asignación real y actualiza el espacio reservado, permitiendo que la lectura de la línea 3 devuelva con éxito el número 5.
EXECUTION CONTEXT AUDIT:
• Declaration Allocation: HOISTED (Mapeado al inicio del script)
• Value Assignment: DELAYED (La asignación física permanece en su línea original)

💡 Análisis técnico: El motor reordena mentalmente tu código interpretando la declaración como si al inicio del archivo hubieses escrito var x; y dejado la asignación x = 5; abajo.

En este código, aunque usamos x antes de declararlo, no aparece un error, sino que obtenemos el valor undefined. Esto se debe a que JavaScript eleva la declaración var x al inicio de su ámbito, pero no la inicialización x = 5. Es como si el código se reescribiera así:

1234567891011 
var x;
console.log(x); // undefined
x = 5;
console.log(x); // 5

Simulación del Comportamiento Interno

Perspectiva del Motor de JS:
🟢 Declaración Pura (Línea 1): Esta es la representación de cómo el motor separa la reserva del espacio. La variable existe formalmente, pero al no tener un dato asignado, adopta de forma predeterminada el tipo undefined.
🟢 Asignación Posterior (Línea 3): Al llegar a este punto en la fase de ejecución, el puntero en memoria sobrescribe el estado inicial y almacena permanentemente el número 5.
INTERPRETATION AUDIT:
• Execution Order: Separation of declaration and initialization confirmed.
• Memory State: Line 2 yields undefined, Line 4 yields 5.

💡 Conclusión visual: Aunque físicamente escribas la variable abajo, este desdoblamiento es el motivo exacto por el cual JavaScript no detiene la ejecución con un error crítico al hacer lecturas previas con var.

El hoisting de funciones funciona de manera un poco diferente. Cuando declaras una función utilizando la sintaxis de declaración de function, tanto el nombre como el cuerpo de la función se elevan. Esto significa que puedes llamar a una función antes de haberla declarado en tu código. A continuación te presento un ejemplo de hoisting de funciones:

1234567891011 
sayHello(); // "Hello, World!"

function sayHello(){
  console.log("Hello, World!");
}

Elevación de Declaraciones de Función

Comportamiento de la Función en Memoria:
🟢 Carga Completa (Línea 1): Durante la fase de compilación, el motor detecta la estructura de tipo declaración de función (function sayHello) e introduce tanto el nombre de la función como su cuerpo de ejecución en el mapa de memoria inicial.
🟢 Invocación Exitosa (Línea 1): Como la definición completa ya se encuentra lista antes de procesar el código línea por línea, la llamada anticipada se ejecuta sin lanzar ningún tipo de error.
HOISTING METRICS AUDIT:
• Allocation Type: FULL HOISTING (Identificador y cuerpo cargados de forma simultánea)
• Execution Status: SUCCESSFUL (Imprime "Hello, World!" correctamente)

💡 Diferencia crucial: Esto solo aplica a declaraciones puras con la palabra clave function. Si defines la función guardándola en una variable (var sayHello = function() {}), el motor la tratará como una variable común y su valor inicial será undefined al intentar llamarla arriba.

En este caso, podemos llamar a sayHello() antes de su declaración porque toda la función se eleva al inicio de su ámbito.

Es importante señalar que la elevación funciona de manera diferente con las declaraciones let y const introducidas en ES6.

12345678910 
console.log(y); // Throws a ReferenceError
let y = 10;

Zona Muerta Temporal (TDZ)

Estado de la Variable en Memoria:
🟢 Fase de Reserva (Línea 1): El motor de JavaScript reconoce la existencia de la variable let y durante la compilación, pero a diferencia de var, la mantiene en un estado estrictamente "no inicializado".
🟢 Bloqueo de Acceso (Línea 1): Intentar leer la variable antes de que el flujo de ejecución pase físicamente sobre la línea de su declaración formal lanza inmediatamente un error crítico de tipo ReferenceError.
ENGINE SECURITY REPORT:
• Initialization State: UNINITIALIZED (Protected by TDZ)
• Runtime Status: CRASHED (ReferenceError)

💡 Concepto clave: La Zona Muerta Temporal comprende todo el espacio de líneas desde el inicio del ámbito de bloque hasta el punto exacto donde se ejecuta la inicialización física de la palabra clave let o const.

Estas declaraciones se elevan, pero no se inicializan y no puedes acceder a ellas antes de la declaración real en tu código. A esto se le suele llamar zona muerta temporal.

Entender el hoisting puede ayudarte a escribir código más limpio y predecible. Sin embargo, confiar en el hoisting puede hacer que tu código sea más difícil de leer y mantener. Como práctica recomendada, se aconseja declarar tus variables al inicio de su ámbito y tus funciones antes de usarlas, independientemente del hoisting. Esto hace que el comportamiento de tu código sea más explícito y más fácil de entender para los demás, incluido tu yo futuro.
